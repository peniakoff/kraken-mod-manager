# Job Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run installs and uninstalls through one server-side FIFO queue that survives a browser reload, blocks duplicate actions per mod, and keeps errors visible.

**Architecture:** A `JobQueue` in the backend runs jobs one at a time; `JobStore`
gains job kinds, hiding and listing. `InstallService` enqueues installs and
uninstalls and re-checks their plans when they start. New queue routes expose
the list, cancel/hide and clear-finished. The frontend `useJobQueue` mirrors
the server list, and the views read one "busy identifiers" map from it.

**Tech Stack:** TypeScript, Node 24, Express 5, Zod contracts, Vue 3, Vitest 5, node:test, pnpm 11.

**Spec:** `docs/superpowers/specs/2026-11-08-job-queue-design.md`

## Global Constraints

- No new dependencies. No `any`, no `@ts-ignore`, no unjustified `!`; `as` only with a comment.
- API data validated with `@kraken/contracts` Zod schemas; fail loudly, no empty catch.
- TDD: each new test is run and seen failing before the code change.
- English code/comments/commits; Conventional Commits; no AI attribution.
- Each task ends with `pnpm lint && pnpm typecheck && pnpm test` green.
- Exact copy:
  - `The install plan changed after it was queued: it now also needs {names}.` ({names} = module names joined with `, `)
  - `{name} already has a queued or running job.` ({name} = registry module name, else the identifier)
  - panel title `Queue`; entry labels `Install {name} {version}`, `Uninstall {name}`, suffix ` (+{n} more)`; status `Queued`; button `Remove`; disabled button texts `Queued`, `Installing…`, `Updating…`, `Uninstalling…`; error bar button `Dismiss`.
- Error codes: `JOB_ALREADY_QUEUED` → 409, `JOB_RUNNING` → 409, `JOB_NOT_FOUND` → 404. `INSTALL_IN_PROGRESS` is removed.

## Review Focus

- A failing or throwing job must not stall the queue: the next job still starts.
- Cancelling a queued job at the moment the queue picks it must either cancel it or run it, never both or neither (check and remove happen synchronously in `JobQueue`).
- A job that fails its start-time re-check must not touch files, the manifest or the journal directory.
- After a reload, a job that was `queued` must still deliver its later `running`/progress/finish events to the panel.
- A hidden or cancelled job must never come back in `GET /api/v1/jobs`, and a running job must never be hideable.

### Task 2: Queue installs and re-check their plan at start

**Files:**
- Modify: `apps/backend/src/install-service.ts`, `apps/backend/src/app.ts` (wiring, error mapping)
- Test: `apps/backend/test/install-api.test.ts`

**Interfaces:**
- Consumes: Task 1 `JobQueue`, `JobStore.create/activeIdentifiers`.
- `InstallService` gets a `JobQueue` (constructor option; `createDefaultDependencies` creates one).
- `startInstall` (same parameters):
  1. checks for duplicates first: target in `activeIdentifiers()` → `InstallServiceError(msg, "JOB_ALREADY_QUEUED")`;
  2. resolves as today, then creates the job and `queue.enqueue(job.jobId, () => this.runInstall(...))`.
- `runInstall`:
  - calls `resolveModulesForInstall` again with the same arguments before writing any journal;
  - every module in the new list whose `identifier`+`version` is not in the accepted list makes the job fail with the "plan changed" message naming those modules;
  - a resolver error fails the job with its message;
  - modules from the accepted list missing from the new list are not installed;
  - the install then runs over the new list.
- `INSTALL_IN_PROGRESS` and its guard in `uninstallOptions` are deleted.

### Task 3: Uninstall jobs and queue routes

**Files:**
- Modify: `apps/backend/src/install-service.ts`, `apps/backend/src/app.ts`, `packages/contracts/src/index.ts` (drop `uninstallResponseSchema`), `docs/ARCHITECTURE.md` (queue section: FIFO, in memory, lost on restart, journal recovery unchanged)
- Test: `apps/backend/test/install-api.test.ts`

**Interfaces:**
- `InstallService`:
  - `startUninstall(kspPath, identifier, alsoRemove): Promise<JobResponse>`. It checks duplicates (target and every `alsoRemove`), validates the selection now (mismatch → `UNINSTALL_PLAN_MISMATCH`), creates a `kind: "uninstall"` job with `alsoRemove`, and enqueues a run. The run re-validates, removes in `removeOrder` inside `withManifestMutation`, and updates the job with `status: "succeeded"`, `phase: "done"`, `removed`. A mismatch at start fails the job with the validation message and removes nothing.
  - `listJobs(): JobResponse[]`;
  - `removeJob(jobId): void` (queued → `queue.cancel` and `jobStore.delete`; finished → `hide`; running → `JOB_RUNNING`; unknown → `JOB_NOT_FOUND`);
  - `clearFinishedJobs(): void`.
  - The old synchronous `uninstall` method is removed.
- Routes:
  - `POST /api/v1/mods/:identifier/uninstall` → 202 `uninstallAcceptedResponseSchema`;
  - `GET /api/v1/jobs` → `jobsListResponseSchema`;
  - `DELETE /api/v1/jobs/:jobId` → 204;
  - `POST /api/v1/jobs/clear-finished` → 204.
  - Register `clear-finished` before `/:jobId` routes. `JOB_RUNNING` and `JOB_ALREADY_QUEUED` map to 409.
